# ۱۴) برآورد سخت‌افزار Ollama + مدل‌های پیشنهادی

## ۱۴.۱ بار کاری واقعی ما

قبل از انتخاب مدل، باید بدانیم LLM دقیقاً چه کاری می‌کند:

| ویژگی | مقدار |
|---|---|
| ورودی | JSON ساختاریافته ~۸۰۰–۱٬۵۰۰ توکن |
| خروجی | JSON فارسی ~۳۰۰–۶۰۰ توکن |
| نوع کار | تفسیر و خلاصه‌سازی ساختاریافته — **نه استدلال ریاضی، نه تولید کد** |
| حساسیت به تأخیر | **پایین** (خارج از مسیر بحرانی، async) |
| نرخ فراخوانی | با کش: ~۵۰–۳۰۰ فراخوان در ساعت بسته به Universe |

**نتیجه مهم:** این یک بار کاری **سبک** است. نیازی به مدل ۷۰B نیست. کیفیت فارسی و پایبندی به JSON مهم‌تر از اندازه مدل است.

## ۱۴.۲ برآورد حافظه

قاعده سرانگشتی:
```
RAM/VRAM موردنیاز ≈ (پارامتر × بیت کوانتیزیشن / 8) × 1.2  +  KV Cache
KV Cache ≈ 0.5 تا 2 GB برای context ۸K
```

| اندازه مدل | Q4_K_M | Q5_K_M | Q8_0 | FP16 |
|---|---|---|---|---|
| 3B | ~2.2 GB | ~2.6 GB | ~3.6 GB | ~6.5 GB |
| 7–8B | ~4.8 GB | ~5.7 GB | ~8.5 GB | ~16 GB |
| 14B | ~9 GB | ~10.5 GB | ~15 GB | ~28 GB |
| 32B | ~19 GB | ~23 GB | ~34 GB | ~64 GB |
| 70B | ~40 GB | ~48 GB | ~72 GB | ~140 GB |

(اعداد تقریبی و شامل سربار context هستند.)

## ۱۴.۵ مدل‌های پیشنهادی برای Ollama

معیارهای انتخاب ما، به‌ترتیب اهمیت:
1. **کیفیت فارسی** (خروجی `summary_fa`)
2. **پایبندی به JSON Schema** (instruction following)
3. **عدم اختراع عدد** (faithfulness)
4. نسبت کیفیت/حافظه

| مدل | اندازه | چرا | هشدار |
|---|---|---|---|
| **`qwen2.5:14b-instruct`** ⭐ | 14B | بهترین تعادل. چندزبانه قوی شامل فارسی، instruction-following عالی، پشتیبانی خوب از JSON | نیاز به ~۱۰GB |
| **`qwen2.5:7b-instruct`** ⭐ | 7B | گزینه پیش‌فرض برای سخت‌افزار متوسط، همان خانواده و رفتار | فارسی ضعیف‌تر از 14B |
| **`gemma2:9b-instruct`** | 9B | کیفیت زبانی خوب، چندزبانه | context کوتاه‌تر (8K) |
| **`llama3.1:8b-instruct`** | 8B | اکوسیستم بزرگ، context ۱۲۸K | فارسی متوسط |
| **`qwen2.5:32b-instruct`** | 32B | بهترین کیفیت قابل اجرا روی سخت‌افزار مصرفی | ۲۴GB VRAM |
| **`mistral-nemo:12b`** | 12B | چندزبانه، context ۱۲۸K | تست فارسی لازم |
| **`phi4:14b`** | 14B | استدلال قوی نسبت به اندازه | فارسی ضعیف |

### مدل‌های کمکی (غیر از تحلیل‌گر اصلی)
| کار | مدل |
|---|---|
| Embedding برای News Dedup | `paraphrase-multilingual-MiniLM-L12-v2` یا `bge-m3` (چندزبانه، فارسی خوب) — از طریق sentence-transformers، نه Ollama |
| Sentiment انگلیسی | FinBERT (کوچک، سریع، تخصصی) |
| Sentiment فارسی | ParsBERT fine-tuned یا zero-shot با همان LLM |

> استفاده از LLM بزرگ برای embedding **اتلاف منابع** است؛ مدل‌های اختصاصی کوچک بهتر و سریع‌ترند.

## ۱۴.۶ پیکربندی عملیاتی Ollama

```env
AI_PROVIDER=ollama
OLLAMA_HOST=http://localhost:11434
AI_MODEL=qwen2.5:14b-instruct-q4_K_M
AI_TEMPERATURE=0.2
AI_TOP_P=0.9
AI_SEED=42
AI_NUM_CTX=8192
AI_TIMEOUT_SECONDS=45
AI_MAX_CONCURRENCY=1
AI_CACHE_TTL_SECONDS=1800
AI_FALLBACK_PROVIDER=null
```

**بهینه‌سازی‌های ضروری:**
| تکنیک | صرفه‌جویی |
|---|---|
| **Cache بر اساس hash فیچرها** | ۶۰–۸۰٪ فراخوان‌ها حذف می‌شوند (فیچرها بین دو کندل کم تغییر می‌کنند) |
| **Trigger مبتنی بر تغییر معنادار** | فقط وقتی `|Δfinal_score| > 3` یا رژیم عوض شد |
| **اولویت‌بندی** | AI فقط برای Top-N رتبه‌بندی‌شده، نه همه Universe |
| **`keep_alive`** | مدل در حافظه بماند تا هزینه بارگذاری مجدد (۱۰–۳۰ ثانیه) حذف شود |
| **Batching منطقی** | تحلیل چند نماد در یک درخواست؟ **نه** — کیفیت افت می‌کند و grounding سخت می‌شود |
| **خلاصه‌سازی ورودی** | فقط فیچرهای مرتبط، نه کل payload |

## ۱۴.۷ برآورد زمان پردازش روزانه

فرض: ۲۰۰ دارایی، ۳ timeframe، هر ۴ ساعت به‌روزرسانی، نرخ hit کش ۷۰٪.

```
فراخوان‌های خام روزانه = 200 × 3 × 6 = 3,600
پس از کش (30٪)        = 1,080
با اولویت‌بندی Top-50  = ~270 فراخوان مؤثر
```

| پیکربندی | زمان هر فراخوان | زمان کل روزانه |
|---|---|---|
| حداقلی (CPU، 7B) | ~۶۰ ثانیه | ~۴.۵ ساعت CPU |
| توصیه‌شده (GPU، 14B) | ~۱۲ ثانیه | ~۵۵ دقیقه |
| ایده‌آل (GPU، 32B) | ~۲۰ ثانیه | ~۱.۵ ساعت |

**نتیجه:** حتی پیکربندی حداقلی قابل استفاده است، مشروط به اولویت‌بندی و کش. این دقیقاً دلیل معماری async و خارج بودن AI از مسیر بحرانی است.
